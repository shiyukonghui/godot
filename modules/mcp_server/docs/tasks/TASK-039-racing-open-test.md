## §A 组织者（先跑；产出方案与观察规则）

**产出**：`docs/reports/RACING-TEST-PLAN.md`（**赛车游戏方案** + **观察规则**）。

1. **方案必须是「可被 MCP 工具真的做出来」的**：目标形态 —
   **一辆能被键盘输入驱动的车 + 一条赛道 + 检查点/圈计时 + 最小 HUD**，
   可在 **headless** 与**窗口化**两种模式下运行（headless 便于自动化取证）。
   写清：场景树结构、C# 脚本（文件名 + 职责 + 关键成员）、输入映射、
   验收判据（**用哪些工具、看什么响应**来证明「车真的动了、圈计时真的在走」）。
2. **方案要留出「试测价值」**：设计成**必须用到相当多样的工具**（场景/节点/脚本/资源/输入/断言/截图/
   信号/属性读写/跨帧观察），**不要**设计成只需三五个工具的小玩具。
3. **观察规则（rubric）**：明确四类观察目标与**判定标准**：
   - **异常**：错误码、超时、pending 超上限、响应异常大、**工具报成功但状态未变**、
     **多次调用才能摸清用法**（连续失败后成功）、工具间**说法矛盾**；
   - **缺失工具**：想做一件事却**没有任何工具**能做（记录你想做什么、试过哪些、为什么都不行）；
   - **可合并**：高频的 2-3 步调用序列（**应当**能合并成一个工具）；
   - **可优化**：参数/返回形状导致的**多余往返**、需要手工字符串处理、错误消息不足以自纠。
4. **不要阻塞**：你只产出方案与规则，**不要**自己去做游戏、**不要**等开发者；
   你的第二阶段（观察）由编排并行启动，见 §C。

## §B 开发者（用 MCP 工具做出这台赛车）

**产出**：`docs/reports/RACING-DEV-LOG.md`（逐条目日志）+ 一个**真的能跑**的 C# 赛车工程。

1. **主手段是 MCP 工具**：凡是能用工具做的（建场景、建节点、写属性、连信号、加脚本、跑游戏、注输入、
   断言状态、截图…）**就用工具做**，并在日志里**逐条**记：`时间 / 工具名 / 参数要点 / 结果（ok or 错误码）/ 学到什么`。
2. **回退必须记录**：凡是**不得不用工具之外的手段**（例如手写 `.cs` 文本、手改 `.tscn`、
   绕过工具直接编辑工程），**必须**在该条日志里写明：**想做什么 / 试过哪些工具 / 为什么不行 / 回退做了什么**。
   → 这是**缺失工具**的证据来源，**比游戏本身更重要**。
3. **摩擦要如实记**：同一个工具**调了几次才成功**？错误消息**够不够让你自纠**？
   有没有「必须先用工具 A 探路再用工具 B」的隐式依赖？→ 逐条写清。
4. **验收（你自己先跑通）**：①工程能起（`dotnet build` + 引擎启动）；②在**游戏端点 9889** 上
   **注入输入**让车动起来，并**用另一个工具**读回位置变化（不是瞬移）；
   ③检查点/圈计时状态**真的变化**（用断言类工具或读属性证明）；
   ④给出**每一条验收判据的实测响应**（含 sha256）。
5. **不做的事**：不修模块；不碰 9877；不写进 `modules/mcp_server/**`；不为了让日志好看而抹掉失败。

## §C 观察者（与 §B **并行**跑；**不阻塞**开发者）

**产出**：`docs/reports/RACING-OBSERVATIONS.md`（**边观察边追加**）。

1. **只读**：**绝不**修改 scratch 工程、**绝不**打断/杀开发者的进程、**绝不**占用它的端口；
   你可以用**第二条连接**（MCP 支持多连接、各自 id 独立）做**只读探测**（`tools/list`、读属性、读场景树）。
2. **观察对象**：`%TEMP%\mcp-racing-test\trace-*.jsonl`（服务端真实调用记录）+ 你自己连接的探测。
   **以追踪为主**，因为它是**服务端的真实事实**，不是开发者的自述。
3. **轮询**：每 30–60 秒读一次新增行（用 `seq` 断段），**边读边记**；
   直到出现 `%TEMP%\mcp-racing-test\DEV-DONE.marker`（开发者写完）或**总预算到顶**（≤ 45 分钟）为止。
4. **记录格式**（每条）：`序号 / 时间(追踪 ts_ms) / 观察到的调用序列 / 事实 / 判为哪一类（异常|缺失|可合并|可优化）/ 证据 / 建议`。
5. **至少给出**：≥3 条**「多次调用才摸清用法」**的实例（连续失败后成功，附完整调用序列与错误码）；
   ≥2 条**缺失工具**线索；≥2 条**可合并**候选（高频 2-3 步序列）；≥2 条**异常或矛盾**实例。
   **没有就如实说没有**（并说明你查了哪些信号）——**不得**为凑数编造。
6. **不阻塞**的含义：开发者**永远不等你**；你也不得要求它改变做法。你的产出是**事后可核对的记录**。

## §D 汇总者（最后跑；把观察变成**可执行的改进清单**）

**产出**：`docs/reports/RACING-FINDINGS.md`。

1. **输入**：§A 的规则、§B 的日志、§C 的观察、两份追踪原始文件、`analyze_mcp_trace.py` 的输出。
2. **必须自己复算**：对 §C 的每条结论**回到追踪原文核对**（行号 + sha256），
   把「**实测**」与「**推断**」分开标注；发现对不上的**明确指出**（对观察者也要纠错）。
3. **产出四张表**（每条都要证据：调用序列/耗时/错误码/文件 sha256）：
   - **异常**（含「报成功但状态未变」「工具间矛盾」「错误消息不足以自纠」）；
   - **缺失工具**（要实现什么能力、当前得靠什么绕过、建议新增的工具**名与签名草案**）；
   - **可合并**（哪几步高频共现、合并后的工具**名与签名草案**、合并的风险）；
   - **可优化**（参数/返回形状/错误消息/往返次数，逐条给**最小改动建议**）。
4. **排序与取舍**：按 **证据强度 × 影响面** 排序；明确标出**不建议做**的（说明为什么）。
5. **对模块的正确性结论**：如果试测**发现了真缺陷**（不是可优化项），
   必须单列一节「**疑似缺陷**」，给出**最小复现**（可直接粘贴的请求 + 期望/实际 + 证据文件 sha256），
   并说明**严重度**。
6. **结论锚点**：写明所有结论测自哪个提交（**D86**）。
