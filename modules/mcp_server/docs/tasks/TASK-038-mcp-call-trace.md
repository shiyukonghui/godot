## 0. 为什么需要它（用户指令）

用户要求：目标收口后做一次**实机游戏开发试测** —— 组织者生成**赛车游戏方案**，交给一个开发子代理用 **MCP 工具**真的做出来，
而**观察者要「观察子代理的操作并进行记录」**，判断异常与可优化点（例如**某工具要多次调用才能摸清正确用法**、
**缺少某些工具**、**若干操作本可合并成一个**）。

**问题**：如果只让开发者「自己写日志」，观察者看到的只是**被观察者的自述**（掐掉的摩擦看不见）。
→ 因此本任务补一个**服务端调用追踪**：**由模块自己**记录每一次工具调用的真实事实。这是观察者的**诚实证据源**。

**硬约束**：**默认关闭**，开启时**不得**改变任何工具的可观察行为（这是**新增旁路能力**，不是行为变更）。

## 1. 要做的事

1. **开关**（按既有端口解析的先例，`DESIGN-DETAIL` §4/GDR-4 的模式）：
   - 命令行 `--mcp-trace=<path>`（若与既有参数风格冲突，用与 `--mcp-port` 一致的形式）；
   - `ProjectSettings: godot_mcp/trace_file`；
   - **默认：关闭**（不写任何文件）。
2. **记录内容**（每次 `tools/call` 一条 JSON Lines；**每行一条、可流式读**）：
   `seq`（单调递增，进程内）、`ts_ms`、`connection`（连接标识）、`id`（JSON-RPC id）、`tool`、
   `args_bytes` 与 **`args`（原样，含超长截断标记）**、`ok`、`error_code`、`error_message`（截断）、
   `duration_ms`、`pending_ms`（若走延迟通道）、`result_bytes`。
   **`tools/list` / `initialize` 也要记**（一次会话的边界与端点是重要事实），但用紧凑形式（不落全量 list）。
3. **健壮性**：写失败**不得**影响工具调用（只记一条 stderr 警告并**自禁**追踪，不刷屏）；
   文件**只追加**；进程退出时**flush**；多连接**交错**时行不撕裂（单线程主线程事件循环天然保证，但要说明）。
4. **隐私/安全**：追踪文件路径**必须在工程内或 `user://`**？——**不必**，它是**本地调试旁路**，
   但必须在报告里说明「它会写下调用参数（可能含工程内容）」，并在文档（`DESIGN-DETAIL` 的新小节，**由决策者落笔**，
   你只需**报给我要写什么**）与启动日志里**明确提示**。
5. **零行为变化证明**：
   - **关闭**时：与 TASK-036 的 `tools/list` 响应**逐字节相同**（贴 sha256 对照）；
   - **开启**时：171 条工具的响应**逐字节相同**（抽 ≥10 个工具 + 全量 `tools/list`）；
   - 门① 在两端点上仍逐字通过。
6. **分析脚本（给观察者用）**：`scripts/analyze_mcp_trace.py` —— 读 JSON Lines，输出：
   - **摩擦信号**：同一工具在短时间内**连续失败后成功**（=「多次调用才摸清用法」）、
     同一工具**重复相同参数**、**错误码分布**（`-32001/-32602/-32000` 等）；
   - **缺失工具线索**：失败的 `tool` 名不存在（`-32601`）或被反复试探的参数名；
   - **可合并线索**：**n-gram 频率**（高频的 2-3 步调用序列 → 候选组合工具）；
   - **异常**：超时、`pending` 超上限、响应异常大、单一工具占比过高（>30% 的总调用）。
   输出**人可读摘要 + JSON**（供组织者消费）。
